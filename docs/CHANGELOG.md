# Changelog · TMMD

## v1.9.0 · 2026-10-29(阅读区版式与材质分层:CDS 口径)

用户:「全都要做。保持透明风格,其他按照刚才的设计仓库的口径来修改就行。」
参考口径:[`Caho1/open-claude-ui`](https://github.com/Caho1/open-claude-ui)(只借结论与数值,不引 React/Tailwind 依赖)。

### A. 版式:层级靠级差与留白,不靠装饰线

| 项 | 旧 | 新 |
|---|---|---|
| H1 | 1.75em + 下边框 | 保留字号变量,去掉边框;`letter-spacing -.02em`,段前 1.6em |
| H2 / H3 / H4 | 1.4 / 1.15 / 1em | 1.45 / 1.18 / 1.02em;H2 段前 2.2em;H4 降一档墨色 |
| 段落 / 列表 | .8em / .2em | .95em / .28em;`li::marker` 用 faint |
| 引用 | 4px 条 | 2px 条(4px 在纸面上像色块);不再叠 wash/plate 背景 |
| 宽表 | 溢出到整页横向滚 | `wrapTables()` 包 `.md-table-wrap`:占满纸面宽、自己滚;单元格 `nowrap` |
| 表格/代码 | 7×12 / 12×14 | 9×14 + `tabular-nums` / 14×16 + `tab-size 2` |
| 中文断行 | normal | `word-break: auto-phrase`(渐进增强,不支持的内核按原样) |

### B. 材质:透明不变,正文抬一档纸

- `.reader` 在窗口底上再叠一层 `--reader-add`(深 52% / 浅 10%),用 `--bg2` 而不是 `--bg` —— 同色叠两层只会把正文压成更黑的洞。
- 合成后:深色 20/40/70% 档 = **61.6 / 71.2 / 85.6%**;浅色 87.4–96.4%。铬层/侧栏仍只走滑条(20–70%)。
- 不再有第二个浓度滑条:`--reader-add` 是 CSS 常量,不进 `applyGlass`。
- **文字晕拆两档**:铬层仍 55(直接压模糊壁纸);正文/编辑器 `--halo-k-reader = --halo-k × .68`,默认峰值 α≈0.34。滑条仍是唯一 SSOT,拖到 0 两边一起停。

### C. 动效:从"到位"变成"有轻重"

- 新增 8 条曲线(swift / enter / out / snap / overshoot / pop / rise / fall)与 5 档时长(120/160/200/300/320ms),`--ease` 默认改为 CDS 的 out 曲线。
- 抽屉/设置小浮层进场 `cds-menu-in`(200ms);按钮按压 `scale(.985)`(`--ease-pop` 120ms);toast 用 overshoot;主题切换用 enter。
- `prefers-reduced-motion` 同步把新增时长压到 1ms。

### D. 阅读区边缘渐隐(7 档非线性)

- 顶部/底部各 28px,7 档 alpha(5.1/14.9/30.2/50.2/70.2/85.1%),顶部/底部各自在"还能滚"时出现。
- `syncReaderFade()` 只在可滚状态翻转时重建 mask;`ResizeObserver` 兜字号/行号/换文档导致的尺寸变化;滚动过程不写样式。
- **真缺陷(本轮实测)**:最初把 16 档 stop 写死在一条 gradient 里,`fade=0` 时底部那组 stop 全塌到 100%,整条 mask 从顶部不透明渐变到 5% —— 正文整页发虚。改成 JS 按当前边缘状态生成单层 gradient;`fade=0` 时直接 `mask-image: none`。

### 收口补充(2026-10-26 傍晚,同版一并发布)

这一节全是"验证顺手撞出来的真缺陷",不是计划里的功能:

**1. ja/en 文案质量 ≠「没有中文残留」** —— 只读审计 337 键 × 3 语后落地 41 条(硬缺陷 9 / 建议 12):
收藏词族统一(en `star` → `favorites`、ja → お気に入り;此前同一颗星按钮的标签写 スター、提示写 お気に入り)、
「回收站」ja 统一 **ごみ箱**(此前 ごみ箱 4 处 / ゴミ箱 2 处混用)、玻璃材质 ja 三套词(グラス/材質/マテリアル)收敛到
ガラス素材、`Recycle Bin` 的 en 大小写统一、`err.moveFail` ja「配置に失敗」→「所定の位置への移動に失敗」、
`dlg.renameSub`「ライブラリ根部」→「ライブラリルート」、`s.glass.floorDesc` 的「70% まで」(会被读成"最高 70%",
与本节标题「可読性の下限」自相矛盾)改成「下限」、设置页描述句尾「。」统一、半角冒号补空格、
语言按钮统一 endonym(`中文 / English / 日本語`)并删掉零引用的死键 `lang.en`。
README 侧同步:ja 的 リーディングマップ→読書マップ · アウトライン→目次 · パレット→配色 · 色味→ウィンドウ地色 · テキストハロー→テキストの影,
en/zh 的 `text halo`/`阅读地图` 也跟上 UI 用词。

**2. `paper` 配色的墨与强调色从来没有生效(死代码)** —— 浅色变量块用的是**裸**属性选择器 `[data-theme="light"]`,
而 `applySettings()` 把 `data-theme` 同时写在 `<html>` 和 `<body>` 上 ⇒ 变量在 body 上又声明一次,
压过 `<html>` 上特异性更高的 `:root[data-theme="light"][data-palette="paper"]`。
实测证据:两种配色的品牌字心像素都是 `#8d2f02`(中性强调),paper 的 `#8f4318` 从未渲染 ——
**板上是 paper、墨是 gruvbox**。修法一行:`:root[data-theme="light"]`,并留注释钉住"`:root` 不能省"。
修后 paper 最坏块 **5.09:1**、最坏 token 仍 **4.53:1**。

**3. PDF 直出:正例终于跑起来了 —— 一跑就撞出两个真缺陷** ——
本机此前找不到候选表里的内核,正例一直立不起来。这次把机器上**真实存在**的 Chromium
(Playwright 自带的 `%LOCALAPPDATA%\ms-playwright\chromium-1248\chrome-win64\chrome.exe`)经
`TMMD_PDF_BROWSER` 测试缝指给应用,正例立刻复现,然后撞出:

- **导出物没有页面底**:`buildStandaloneHtml` 只写 `body{background:transparent}`(应用里那是"让开玻璃窗"的意图),
  导进浏览器就成"白纸 + 浅色字",打印更是白纸打浅字 ⇒ **PDF 是 1441 字节的空页(0 字体、0 文本算子)而命令照样返回成功**。
  修法:导出物显式铺一层实色页面底(配色跟主题走);打印一律"白纸深字",且必须**重设变量**
  (正文用的是 `var(--fg)`,只写 `body{color:#111}` 压不过继承)+ 复刻一份浅色 token 值
  (浅色那组被 `:root[data-theme="light"]` 的选择器关在门外)。**深色是默认主题,所以这一条是致命的。**
- **"产物出现"会被上一轮的产物顶替**:同一个文档导出第二次时,目标路径上那份旧 PDF 就满足

- 候选表**仍然只认真浏览器**:ego lite 不进去(它不产文件,加进去只会把"找不到内核"这句清楚的话变成含糊的"PDF 未生成")。

## v1.8.12 · 2026-10-26(PDF 导出不再可能永久卡住 + 卸载器把文件关联收回)

这一版只有两件事,但都是"用户会真的撞上"的那种。

### 1. 导出 PDF:判据从"进程退出"换成"产物出现"

拿本机唯一内核(ego lite 的 Chromium,`TMMD_PDF_BROWSER` 指过去)做正例时量到的是病灶:

- 应用起的无头进程(`--headless=new … --print-to-pdf=<绝对路径>`)活 **157 秒**:整棵进程树
  (gpu / network / storage / renderer / crashpad)都在,`%TEMP%` 与全盘热点目录里**没有任何新 PDF**,进程也不退出。
- 旧代码 `cmd.status()` 就是**等它退出** ⇒ 用户点「导出 PDF」永久停在"正在生成 PDF…"(跑道侧表现为 60s evaluate 超时)。
- 换旧式 `--headless` 再试:同样不产文件 —— 所以**旗号不是问题**,代码里仍是 `--headless=new`。

修法四件(都在 `export_pdf`):

| # | 做法 | 为什么 |
|---|---|---|
| 1 | 判据改成**产物文件出现**,且大小连续两次一致才算写完 | 有些分支打印完也不退出;半截文件不能算成功 |
| 2 | **30s 硬上限**(`PDF_WAIT_SECS`) | 到点必须收摊,不能让 UI 无限等 |
| 3 | 到点 `taskkill /PID <我们起的那个> /T /F` | `kill` 只收直接子进程,无头浏览器是一窝;实测残留 **0** |
| 4 | 每次调用给一个一次性 `--user-data-dir=<temp>`,用完删 | 不抢用户正开着的浏览器 profile,也不会被"交接给已有实例"(那条路根本不打印) |

**文案纪律**(本轮踩到并记住):后端每个中文错误串都必须被前端 `ERR_MAP` + `ERR_TAIL_MAP` **整段吃掉** ——
E11 会把 `lib.rs` 里全部中文错误串喂 `trErr`,EN 面留一个汉字就红。第一版新文案写成
`PDF 未生成(等了 30 秒没等到文件);…`,其中"等了…没等到文件"没有映射规则 → 直接红;改成能整段吃掉的短句后绿。

### 2. 卸载器把文件关联收回(否则卸完 `.md` 是死指向)

真卸了一次(2026-10-26)才看见:安装器按 Tauri 的 `APP_ASSOCIATE` 把 `.md` / `.markdown` 的默认 ProgID 写成
`Markdown`,而卸载器只删 `HKCU\Software\Classes\Markdown` 本体,**留着扩展名那一侧指着它** → 卸完双击 `.md`
落到"选择打开方式"。附带 `TMMD.md` 与 `OpenWithProgids` 里的死项也留着。

修法 = `bundle.windows.nsis.installerHooks` → `src-tauri/nsis-hooks.nsh` 的 `NSIS_HOOK_POSTUNINSTALL`:

- 扩展名默认值**只在当前值仍是我们写的 `Markdown` 时**才删(用户后来改成别的绝不碰);
- 删 `TMMD.md` / `.md`·`.markdown` 的 `OpenWithProgids` 项 / `Applications\tmmd.exe`(都指向已卸走的 exe = 死链);
- **不碰** `…\FileExts\.md\UserChoice`(那是用户自己的默认应用选择,系统也不让程序改)。

`.nsh` 里**只用 ASCII 注释**:makensis 按机器 ANSI 代码页读 `.nsh`,中文注释会让它解析失败(同 `tools/*.ps1` 的纪律)。

## v1.8.10 · 2026-10-25(工具栏:窗口够宽却一直折叠 —— 判据自指)

用户实拍(1502px 宽):主题 / 设置 / 玻璃三个按钮缩在 ⋮ 里。

**复现**:1502px 窗口、`#actions.clientWidth = 170`、栏内 4 个按钮、抽屉里 3 个。

**根因**:旧判据是 `栏内各项宽 + 每项 5px ≤ #actions.clientWidth`,而 `#actions` 最终是
`flex: 0 1 auto; min-width: 148px` —— **它的 clientWidth 就是自己的内容宽**,拿它对内容求和是自指:

- 每项都多算一个 5px(gap 只在项与项之间,N 项只有 N−1 个 gap)⇒ 折到 `min-width: 148px` 后不等式恒真;
- 折叠会让容器跟着变窄 ⇒ "放不下"永远成立 ⇒ **折进去再也回不来**(用户看到的就是这个)。

**第二处根因(同一条链上)**:`.tabbar` 是 `flex: 1 1 auto` —— 它把顶栏的空余**全部吃掉**
(实测单标签就把 tabbar 撑到 1099px),工具栏只剩 170px。改成 `flex: 0 1 auto`:标签栏按内容宽走,
多余空间交给 brand 的 `margin-left: auto`;标签多时照样可缩、可横向滚动。

**新判据**:整条顶栏的**自然宽度** ≤ 顶栏可用宽度(可见项真实尺寸 + gap,减去顶栏 padding,留 2px 防抖)。
按钮折进抽屉后 `offsetWidth = 0`,自然宽走缓存;切图标/文字模式时缓存作废、且先把抽屉里的全部归位再量。

|---|---|---|
| 1502px 宽窗 | 栏内 4 个 + ⋮(3 个被藏)| **栏内 7 个,⋮ 隐藏** |

- **实测(副屏真实合成像素,同一张壁纸)**:跨表面边界同高度取样(顶栏→正文、侧栏→正文、侧栏底→正文、设置页导航→主体)Δ = 0.0–1.4 luma → **"一整块"成立**;正文留白沿壁纸连续变化(135→133→108→96→103→131→127),无分块跳变。最坏情况对比度(`--fg` 压在窗内最亮壁纸带):conc 45 → 中位 3.71:1 / 最坏 2.15:1;conc 70 → 6.35:1 / 3.21:1(纯白壁纸模型对应 2.17:1 / 4.55:1)。**默认取 40%**(实测见 v1.8.1)。
- 另注:只设 `DWMWA_USE_HOSTBACKDROPBRUSH=1` 而不接 WinAppSDK 的 composition target **无任何视觉变化**(实测前后像素完全一致);pebrel 那条现代路线需要 ~200 行 COM 互操作(WinAppSDK 1.8 + `DesktopWindowTarget`),而我们的 WCA 回落路径与它的回落路径同级。
- **内容板不再是补丁**:31 处 `background: var(--bg2|--bg3|--code-bg|--bg)` 换成 `--surface-plate`(浓度 +22)/`--surface-plate-strong`(+40);代码块不再强制不透明。
- 修:`applyAtmos` 还在往存档写已废的 `base/chrome/reader/pop`(全是 `undefined`)→ 氛围档按钮失效;`.setpage-search` 在设置页里又垫了一层窗口级浓度。
- 实测(副屏抓真实合成像素):Mica 确认真机生效(`backdrop 1 → 2`);系统 Win11 backdrop(2/3)**不透明**,透不出壁纸 → "看得见的整块玻璃"只能走 legacy accent 通道。最坏情况对比度已量化(45% 浓度下亮壁纸处约 2.1:1,70% 约 4.5:1);**默认取 40%**(用户 2026-10-25 定调,实测值见 v1.8.1)。
